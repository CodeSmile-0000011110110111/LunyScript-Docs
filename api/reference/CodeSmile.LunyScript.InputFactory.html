The Input surface inside Build(): names the local player whose actions this script reads. It hides UnityEngine.Input inside a Script the same way Transform hides UnityEngine.Transform.

public readonly struct InputFactory
Expand Details ...

Examples

var move = Input.ForPlayer(0).Vector2("Move");
var fire = Input.ForPlayer(0).Button("Fire");
On.Ready(Input.Cursor.Lock(), Input.Cursor.Hide());

Remarks

Action reads are always a named local player's input, never the machine's. There is no member here that reads a key or a device: an action is resolved for one local player, so a four-player split screen is four declarations and not one global read that every player shares. That is what the accepted design means by not deriving local players from global device polling. The machine cursor is the exception: Cursor is one lock and one visibility flag for the whole machine.

Which backend supplies the actions is a runner service, not a script's business. The Input surface names no package. CodeSmile.LunyScript.Input is the Input System adapter and the only place in the product that references that package; with no adapter installed every action reads its resting value and says so once.

This surface's shape is provisional. It implements the recorded recommendation of the open decision contract-input-actions, which is one player-scoped typed action handle for both the values and the occurrences. The alternative that decision holds open repeats the player and the name at each use instead. Nothing below this surface depends on which of the two is chosen.

Examples

Remarks

A local player is numbered from 0, which is the first player on this machine. The number is what the configured backend pairs a device with. A named player is not accepted here: Define has no player kind, and a typed player identity is the open decision contract-player-identity.
