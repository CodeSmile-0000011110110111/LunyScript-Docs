Class TransformStreamInbox

Namespace
CodeSmile.LunyScript
Assembly
ApiSource.dll

Holds the transform streams that arrived since the last tick drained them, in one buffer the inbox owns. Every INetworkProvider uses one, so that the receive side of the stream is written once rather than once per backend.

public sealed class TransformStreamInbox
Inheritance
object
TransformStreamInbox

Remarks

Why this exists rather than a queue of byte arrays. A stream arrives on every tick of every peer that is not the authority. Handing back a fresh array per stream would allocate on every one of those ticks, which AGENTS.md rule 29 forbids and which none of rule 31's five relaxations covers. The arriving bytes are copied into one buffer instead, and TryDequeue(out byte[], out int, out int) hands back the offset and length of a stream inside it.

How the buffer is reused. The write cursor returns to the start on the first append after the queue has been drained. That is deliberately not "on the last dequeue": a caller reads the bytes after TryDequeue(out byte[], out int, out int) has returned, and resetting there would let the next arriving stream overwrite them while the caller was still reading. Resetting on the next append instead means a view stays readable until new bytes arrive, and a view that old is stale in any case.

What it assumes about threads. Nothing here is thread safe. Both providers append from the netcode backend's own receive callback and drain from ScriptRunner.TickFrameUpdate, and both of those run on the main thread in separate phases of one frame.

Remarks

A stream travels as an unnamed message, which carries no name of its own, so a provider is handed every unnamed payload in the session including ones this product did not send. This is what lets a provider drop those before copying them: without it, another system's large payload grows the provider's receive buffer and this inbox's buffer to its size, and neither ever shrinks. It is three byte comparisons and not a parse.

The reader checks the same three bytes again when it decodes; that is not a duplicate for the sake of it, because a payload can also arrive through a provider that never saw it as an unnamed message.
