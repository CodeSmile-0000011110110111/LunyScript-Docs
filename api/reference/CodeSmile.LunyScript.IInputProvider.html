LunyScript API Reference

Interface IInputProvider

Namespace
CodeSmile.LunyScript
Assembly
ApiSource.dll

What an input backend provides to the InputGateway: the resolution of a declared action name to something the backend can read, the four value reads, the start of each frame's occurrences and the three occurrence tests, interactive rebind start, cancel and poll, the bound control path, binding reset, the binding overrides a Settings document saves and loads, and local player pairing. Script code never sees this type; it sees the Input surface, When.Input, When.Player, handle.Rebind().As, handle.BoundControl, handle.ResetBinding() and .Bindings(Input.ForPlayer(n)). Cursor lock and visibility are not on this interface.

Examples

runner.InputGateway.UseProvider(new FakeInputProvider());

Remarks

Two implementations exist and the tests that matter run against both. FakeInputProvider is a second real implementation rather than a mock, in the same way FakeNetworkProvider is: it holds declared actions and the values a test gives them, which is what makes every input test runnable in Edit Mode with no device and no window. InputSystemProvider in CodeSmile.LunyScript.Input is the Input System one, and it is the only place in the product that references that package.

A value read returns the last value the action received. The backend keeps a copy of each resolved action's value and press state, written while the backend processes its input, and a read returns that copy without asking a device. The same copy answers in On.FixedUpdate, in On.Update and in every other event, whichever of those phases the backend processes its input in. An action that has received nothing reads its resting value.

An occurrence is delivered once, in the first frame update after it was received, and is never replayed. The backend records the occurrences each action receives, and BeginFrame() hands everything received since the previous call to the frame that is starting. An occurrence the scripts of that frame did not ask about is gone, which is what the accepted design requires of input while a menu is open.

Nothing here throws because a device is absent. A player with no paired device reads the resting value of every action, the way an offline INetworkProvider reports no authority: a missing device is a state, not an exception.

BeginFrame()

Starts the occurrences of a new frame: from this call until the next one, Occurred(int, InputPhase) answers whether the action received that occurrence between the previous call and this one. Called once per frame by the gateway, before any script instance runs. Must allocate nothing.

Remarks

Several input updates can fall between two calls, such as several fixed steps of one frame when the backend processes its input before each fixed step; all of them belong to the frame that starts here, and one occurrence received in two of them is delivered once.

Parameters

The identity, 0 for nobody and for a number the backend cannot hold.

Remarks

The identity changes when a different person takes the number, and stays the same when the same person's device is lost and regained or re-paired, which is what the settled contract-player-identity answer asks of a participant. A backend must not hand out the same identity to two people during its lifetime; the gateway maps it to a counter of its own, so two backends may use the same numbers.

Two numbers that answer the same identity name one person. A backend that pairs its own players answers its host's identity on numbers 0 and 1, and the gateway then gives both numbers one participant and counts that person once.
