Remarks

This type exists to be the one interception point. Before it, LunyScriptUsageException and LunyScriptContractException were both sealed and both derived from InvalidOperationException, so they were siblings whose only shared ancestor also catches framework failures that have nothing to do with LunyScript. A debugger filter, a catch block or a diagnostic layer could not select "everything LunyScript threw"; now one type name does it.

The .NET argument types are deliberately not kept. C# has single inheritance, so an exception cannot be both an ArgumentNullException and a LunyScriptException, and the choice between them was made in favour of the base class: a user of a scripting API is not writing general .NET code against these types and should almost never catch one at all, because they name a mistake to fix rather than a condition to handle. Recorded in docs/api-changes.md.

An exception that knows the authored location presents it as the topmost stack frame. A block is composed inside Build() and executed much later, so the user's script line is not on the call stack when the block fails. A throw out of Build() carries the location from its own call site; a throw while a block runs is given the running block's location by ScriptRunner.ReportBlockFailure, through AttachBlockContext, because the checks that raise it are too far from the block to name it themselves; which of the two wins, and when there is neither, is docs/console-navigation.md's "Which authored location a diagnostic carries". StackTrace prepends Location in Unity's own stack-frame format, which is what UnityEngine.StackTraceUtility.ExtractStringFromExceptionInternal reads through this virtual property, so the Console prints the user's own line as the topmost frame. It does not navigate there. A Console entry's double-click target is the file and line Unity fills in from the live call stack when the entry is written; where that lands differs by path and is measured in docs/console-navigation.md. See SourceLocation for how the location is captured.

Remarks

The added line is Unity's own frame format, Type:Method() (at path:line), which is what StackTraceUtility produces, so a reader of the Console text sees the user's own line first. Nothing is removed: the real frames follow, so the failure is still diagnosable by a maintainer.

This changes what the entry prints and not where a double-click on it goes. Unity chooses that target from the live call stack at log time rather than from this string. docs/console-navigation.md records the measurement.

Where that target lands depends on who wrote the entry, and this property moves it on neither path. Where ScriptRunner.ReportBlockFailure reports the failure, LunyScript writes the entry itself, so it navigates to the line that reported the exception. Where the exception escapes instead - out of ScriptRunner.RaiseReady into LunyScriptBehaviour.Start, or out of Build() - LunyScript writes no entry and no error line at all, so there is no link of ours: Unity logs it, and the entry opens whatever called into the code that threw. The frame this property prepends is printed either way, and Unity links every printed frame that carries source information.
