One Sync.Position, Sync.Rotation or Sync.Scale as the build recorded it: which channel, at which cadence, and which slots hold the per-object bookkeeping the network tick needs. Built by ScriptBuildContext and read by ScriptRunner; a script never sees one.

public readonly struct TransformSyncDeclaration

Remarks

The shadow slots are the one part worth reading twice, because they mean two things at once and that is deliberate. On the peer with authority they hold the last value it put in the stream. On every other peer they hold the last value it took out of one. Both are the same fact - the value the two ends agree on - which is exactly what a change is measured against, so the position channel's change encoding needs no second set of slots to decode with.

The rotation channel uses one shadow slot, not three, and what it holds is not a coordinate. A rotation is sent whole rather than as a change, so the only thing the authority needs to remember is the 32 bits it last sent, and ShadowSlotX holds exactly those, as a Number, which carries a 32-bit integer without rounding. ShadowSlotY and ShadowSlotZ are CodeSmile.LunyScript.ScriptBuildContext.NoShadowSlot there: a negative index cannot address a slot, so a path that read one by mistake fails its bounds check rather than reading an unrelated variable.

The slot latching that this object's value was already reported as outside what the stream's encoding holds. Set once and never cleared, so the report is made once for an object and not again. Only the scale channel has one: it is the only channel that sends a value rather than a change, so it is the only one with no second form to fall back to.
