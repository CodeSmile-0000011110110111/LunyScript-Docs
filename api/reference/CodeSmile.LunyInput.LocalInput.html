The input of the players on one machine, read from an Input System action asset: each player's actions as typed handles, the phases each action received in the frame that is running, the pairing of devices to players, interactive rebinding, and the binding overrides a game stores.

Remarks

The action asset owns the bindings and the processors. Nothing here creates an action, binds a key or applies a processor: it finds the action a caller names, checks it produces the kind the caller asked for, and reads it.

A read returns the last value the action received. Each action's value and pressed state are recorded while the Input System processes input: in the action's own started, performed and canceled callbacks and at the end of every input update, through InputSystem.onAfterUpdate. A read returns that record and asks no device, so FixedUpdate and Update read the same value whether the Input System processes input before each frame, before each fixed step or when the game calls InputSystem.Update. An action that received nothing reads its resting value.

Three setups, chosen by the constructor. new LocalInput(actions) is one player, player 0, present from the start on every device; pairing is refused. new LocalInput(actions, 4) pairs up to four players itself: each gets its own copy of the action asset and an InputUser. The first button press makes the host, player 0, who reads every device until pairing first opens; after that each press on a device nobody holds pairs it while pairing is open, and the guests are players 1, 2 and 3. new LocalInput() reads the players of the scene's PlayerInput components, which PlayerInputManager pairs.

Disposal. Dispose() releases the action copies, the InputUsers and every Input System subscription. A LocalInput still alive when the application quits, which in the Editor is when Play Mode ends, disposes itself then, so a forgotten one holds no device and records nothing in the next Play Mode session.

Assets/CodeSmile/LunyInput/README.md is the contract, and LunyScript's InputSystemProvider reads its players through this type.

Remarks

A PlayerInput for a player index always wins, because that is where the Input System keeps that player's paired devices; the asset is what a single-player game uses, where there is nothing to pair.

The asset is enabled here, because an action that is not enabled reads its resting value forever, which reads exactly like a wrong binding. A PlayerInput's own actions are left alone: that component enables and disables them itself.

Examples

var input = new LocalInput(actions, 4);

Remarks

The first player to pair is the host, player 0, who stays for as long as this LocalInput lives. Every later player is a guest on the lowest free index from 1 up.

The solo start. Until pairing first opens, the first button press on a device the asset can use makes the host, and the host's actions read every device, so a game for one player needs no pairing code. OpenPairing() for the first time ends it: the host keeps their InputUser and Identity, their actions read no device, and the next device pressed becomes the host's, with pairing open or not. A guest pairs only while pairing is open. The press that pairs a device is not delivered to the actions of the player it pairs.

Each player gets its own copy of actions, made here with Object.Instantiate, so the actions of two players are different InputAction objects and one gamepad cannot drive both. A copy is restricted to the devices paired with its player and is disabled while nobody holds the index. PlayerInput components are not read by this setup.

A pairing request, a press on a device nobody holds or a Leave(), is applied at the end of the input update that received it, or of the next one for a leave.

Exceptions

LunyInputException

actions is null or players is below 1.
