Remarks

This assembly compiles only when the Input System package is installed. Its assembly definition carries a version define, LUNY_INPUTSYSTEM from com.unity.inputsystem 1.8.0 or newer, and a matching define constraint, which is the same arrangement CodeSmile.LunyScript.Netcode uses for Netcode for GameObjects. The ownership board's P01 row is what authorises this one reference: "new O02 authorization supersedes the old all-assembly package ban for this adapter", and the core stays package-independent.

The configured action asset owns the bindings and the processors. Nothing here creates an action, binds a key or applies a processor: it finds the action the script named, checks it produces the kind the script declared, and reads it. Where a PlayerInput component exists for a local player, its own actions are used, so device pairing is the Input System's and not this provider's.

Every read is polled and frame-scoped. The three occurrences map to the Input System's own frame queries, so nothing is queued, nothing is replayed and no callback is subscribed. That is what keeps an occurrence from arriving outside a frame and what keeps a paused frame's edges from being delivered later.

Three setups, chosen by the constructor. new InputSystemProvider(actions) is one player: local player 0 is present from the start on every device and pairing is refused. new InputSystemProvider(actions, 4) pairs up to four local players itself: each gets its own copy of the action asset and an InputUser, and Input.Pairing.Open() pairs a device on a button press. With PlayerInput components in the scene and no local player count, their players are observed and PlayerInputManager owns the pairing. docs/proposals/local-player-pairing.md is the contract.

Remarks

A PlayerInput for a local player always wins, because that is where the Input System keeps that player's paired devices. The asset is what a single-player project uses, where there is nothing to pair and a PlayerInput component would be ceremony.

The asset is enabled here, because an action that is not enabled reads its resting value forever and that reads exactly like a wrong binding. A PlayerInput's own actions are left alone: that component enables and disables them itself.

Creates a provider that pairs up to localPlayers local players itself. Nobody is present until a script opens pairing and someone presses a button.

Parameters

InputActionAsset

Examples

runner.InputGateway.UseProvider(new InputSystemProvider(actions, 4));

Remarks

Each local player number gets its own copy of actions, made here with Object.Instantiate, so the actions of two players are different InputAction objects and one gamepad cannot drive both. A copy is restricted to the devices paired with its player and is disabled while nobody holds the number.

PlayerInput components are not read by this setup: it owns the pairing, and a scene that pairs with PlayerInputManager uses the other constructors. Call Dispose(), or install another provider, which disposes this one, to release the copies and the InputUsers.

Remarks

The identity changes when a different person takes the number, and stays the same when the same person's device is lost and regained or re-paired, which is what the settled contract-player-identity answer asks of a participant. A backend must not hand out the same identity to two people during its lifetime; the gateway maps it to a counter of its own, so two backends may use the same numbers.

UpdatePairing()

Applies every pairing change requested or detected since the last call. Called once per frame by the gateway before any script instance runs, so every script sees the same players during one frame. Must allocate nothing when nothing changed.

public void UpdatePairing()

Remarks

Leaves first, then every button press on a device nobody held, in the order the Input System reported them. A press goes to the lowest-numbered player whose device is lost, who keeps their InputUser, and otherwise, while pairing is open, to the lowest free number as a new InputUser.
