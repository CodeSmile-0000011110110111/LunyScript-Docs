Remarks

This assembly compiles only when the Input System package is installed. Its assembly definition carries a version define, LUNY_INPUTSYSTEM from com.unity.inputsystem 1.8.0 or newer, and a matching define constraint, which is the same arrangement CodeSmile.LunyScript.Netcode uses for Netcode for GameObjects, and LunyInput's assembly carries the same pair. The core stays package-independent.

LunyInput does the work; this type translates. A LocalInput finds and records the actions, pairs the devices, captures rebinds and lists the binding overrides, and C# beside the scripts can read the same players through Input and LocalPlayer(int). This type maps a script's declaration to a LunyInput record and back to the numbers InputGateway keeps, maps the enums, and adds what is LunyScript's own: the two numbers of the host, the frame window and pairing at the runner's frame start. Assets/CodeSmile/LunyInput/README.md states the boundary.

Numbers 0 and 1 both name the host. With players the LocalInput pairs, LunyScript's local player numbers 0 and 1 are LunyInput's player 0, the host, and number n from 2 up is LunyInput's player n - 1, so LocalPlayerCapacity is one more than the players it can hold. docs/proposals/local-player-pairing.md is the contract. In the other two setups a number is the player index unchanged.

The three occurrences are handed to the next frame update. Started, Performed and Canceled are the action's own phases; the record collects the ones received since the gateway's last BeginFrame(), which hands them to the frame that is starting and drops the ones the previous frame held. Several input updates in one frame deliver one occurrence, and an occurrence nobody read in its frame is not delivered later. The gateway also applies pairing at its frame start, through UpdatePairing(), so every script of one frame sees the same players.

Three setups, chosen by the constructor. new InputSystemProvider(actions) is one player: local player 0 is present from the start on every device and pairing is refused. new InputSystemProvider(actions, 4) pairs up to four local players itself, with the solo start LocalInput describes. With PlayerInput components in the scene and no local player count, their players are observed and PlayerInputManager owns the pairing. InputSystemProvider.For(input) reads a LocalInput the caller made and keeps.

Remarks

A PlayerInput for a local player always wins, because that is where the Input System keeps that player's paired devices. The asset is what a single-player project uses, where there is nothing to pair and a PlayerInput component would be ceremony.

The asset is enabled here, because an action that is not enabled reads its resting value forever and that reads exactly like a wrong binding. A PlayerInput's own actions are left alone: that component enables and disables them itself.

Examples

runner.InputGateway.UseProvider(new InputSystemProvider(actions, 4));

Remarks

The first player to pair is the host, and local player numbers 0 and 1 both name the host for as long as this provider lives: a leave of either changes nothing. Every later player is a guest on the lowest free number from 2 up to localPlayers.

The solo start. Until a script first opens pairing, the first button press on a device the asset can use makes the host, and the host's actions read every device, so a game for one player needs no pairing line. Opening pairing for the first time ends it: the host keeps their InputUser and their participant, their actions read no device, and the next device pressed becomes the host's, with pairing open or not. A guest pairs only while pairing is open, and opening pairing again later keeps the host's device.

Each player gets its own copy of actions, so the actions of two players are different InputAction objects and one gamepad cannot drive both. PlayerInput components are not read by this setup: it owns the pairing, and a scene that pairs with PlayerInputManager uses the other constructors. Call Dispose(), or install another provider, which disposes this one, to release the copies and the InputUsers.

Exceptions

LunyScriptUsageException

For(LocalInput)

Creates a provider that reads a LocalInput the caller made, so the scripts and the C# beside them read the same players, the same pairing and the same rebound controls.

public static InputSystemProvider For(LocalInput input)

Parameters

Type Name Description
LocalInput
input

The LocalInput to read; it must not be disposed.

Returns

InputSystemProvider

The provider, to install with UseProvider(IInputProvider).

Examples

m_Input = new LocalInput(m_Actions, 4);
LunyScriptRuntime.DefaultRunner.InputGateway.UseProvider(InputSystemProvider.For(m_Input));

Remarks

The caller keeps the LocalInput and disposes it: releasing or replacing this provider leaves it working. While this provider is installed, the runner applies the LocalInput's pairing at its frame start, so every script of one frame sees the same players; C# reads after that start see them too. With players the LocalInput pairs, numbers 0 and 1 both name its player 0, the host, and number n from 2 up is its player n - 1.

A method rather than a fourth constructor, because the C# compiler reads every constructor's parameter types to choose one, so a constructor taking a LocalInput would make every assembly that calls new InputSystemProvider(actions) reference LunyInput's assembly.

Parameters

Type Name Description
int
localPlayerIndex

Which local player number, from 0.

Returns

long

The identity, 0 for nobody and for a number the backend cannot hold.

Remarks

The identity changes when a different person takes the number, and stays the same when the same person's device is lost and regained or re-paired, which is what the settled contract-player-identity answer asks of a participant. A backend must not hand out the same identity to two people during its lifetime; the gateway maps it to a counter of its own, so two backends may use the same numbers.

Two numbers that answer the same identity name one person. A backend that pairs its own players answers its host's identity on numbers 0 and 1, and the gateway then gives both numbers one participant and counts that person once.
