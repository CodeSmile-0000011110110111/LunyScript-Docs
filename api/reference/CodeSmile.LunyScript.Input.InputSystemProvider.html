Remarks

This assembly compiles only when the Input System package is installed. Its assembly definition carries a version define, LUNY_INPUTSYSTEM from com.unity.inputsystem 1.8.0 or newer, and a matching define constraint, which is the same arrangement CodeSmile.LunyScript.Netcode uses for Netcode for GameObjects. The ownership board's P01 row is what authorises this one reference: "new O02 authorization supersedes the old all-assembly package ban for this adapter", and the core stays package-independent.

The configured action asset owns the bindings and the processors. Nothing here creates an action, binds a key or applies a processor: it finds the action the script named, checks it produces the kind the script declared, and reads it. Where a PlayerInput component exists for a local player, its own actions are used, so device pairing is the Input System's and not this provider's.

A read returns the last value the action received. Each resolved action's value and press state are recorded while the Input System processes input: at the end of every input update the game reads, through InputSystem.onAfterUpdate, and in the action's own started, performed and canceled callbacks. A read returns that record and asks no device, so a script reads the same value in On.FixedUpdate and in On.Update whether the Input System processes input before each frame, before each fixed step or when the game calls InputSystem.Update. Before the first record an action reads its resting value.

The three occurrences are the action's own phases. Started, Performed and Canceled are recorded in the callbacks of the same names and handed to the next frame update by BeginFrame(), which the gateway calls once per frame. Each is delivered in that frame and then dropped: several input updates in one frame deliver one occurrence, and an occurrence nobody read in its frame is not delivered later. No authored block runs inside an Input System callback; the callbacks only record numbers and set bits.

Three setups, chosen by the constructor. new InputSystemProvider(actions) is one player: local player 0 is present from the start on every device and pairing is refused. new InputSystemProvider(actions, 4) pairs up to four local players itself: each gets its own copy of the action asset and an InputUser, and Input.Pairing.Open() pairs a device on a button press. The first player to pair is the host, whom numbers 0 and 1 both name, and the others are guests 2, 3 and 4. With PlayerInput components in the scene and no local player count, their players are observed and PlayerInputManager owns the pairing. docs/proposals/local-player-pairing.md is the contract.

Remarks

A PlayerInput for a local player always wins, because that is where the Input System keeps that player's paired devices. The asset is what a single-player project uses, where there is nothing to pair and a PlayerInput component would be ceremony.

The asset is enabled here, because an action that is not enabled reads its resting value forever and that reads exactly like a wrong binding. A PlayerInput's own actions are left alone: that component enables and disables them itself.

InputSystemProvider(InputActionAsset, int)

Creates a provider that pairs up to localPlayers local players itself. Nobody is present until a script opens pairing and someone presses a button.

public InputSystemProvider(InputActionAsset actions, int localPlayers)

Parameters

Type Name Description
InputActionAsset
actions

The action asset each local player's copy is made from.
int
localPlayers

How many local players can pair, the host included, from 1.

Examples

runner.InputGateway.UseProvider(new InputSystemProvider(actions, 4));

Remarks

The first player to pair is the host, and local player numbers 0 and 1 both name the host for as long as this provider lives: a leave of either changes nothing. Every later player is a guest on the lowest free number from 2 up to localPlayers.

Each player gets its own copy of actions, made here with Object.Instantiate, so the actions of two players are different InputAction objects and one gamepad cannot drive both. A copy is restricted to the devices paired with its player and is disabled while nobody holds the number.

PlayerInput components are not read by this setup: it owns the pairing, and a scene that pairs with PlayerInputManager uses the other constructors. Call Dispose(), or install another provider, which disposes this one, to release the copies and the InputUsers.

Exceptions

LunyScriptUsageException

actions is null or localPlayers is below 1.

BeginFrame()

Starts the occurrences of a new frame: from this call until the next one, Occurred(int, InputPhase) answers whether the action received that occurrence between the previous call and this one. Called once per frame by the gateway, before any script instance runs. Must allocate nothing.

Remarks

Several input updates can fall between two calls, such as several fixed steps of one frame when the backend processes its input before each fixed step; all of them belong to the frame that starts here, and one occurrence received in two of them is delivered once.

ParticipantAt(int)

public long ParticipantAt(int localPlayerIndex)

Parameters

Type Name Description
int
localPlayerIndex

Which local player number, from 0.

Returns

long

The identity, 0 for nobody and for a number the backend cannot hold.

Remarks

The identity changes when a different person takes the number, and stays the same when the same person's device is lost and regained or re-paired, which is what the settled contract-player-identity answer asks of a participant. A backend must not hand out the same identity to two people during its lifetime; the gateway maps it to a counter of its own, so two backends may use the same numbers.

Two numbers that answer the same identity name one person. A backend that pairs its own players answers its host's identity on numbers 0 and 1, and the gateway then gives both numbers one participant and counts that person once.

UpdatePairing()

Applies every pairing change requested or detected since the last call. Called once per frame by the gateway before any script instance runs, so every script sees the same players during one frame. Must allocate nothing when nothing changed.

public void UpdatePairing()

Remarks

Leaves first, then every button press on a device nobody held, in the order the Input System reported them. A press goes to the lowest-numbered player whose device is lost, who keeps their InputUser, and otherwise, while pairing is open, to the host while nobody holds the host and to the lowest free guest number after that, as a new InputUser.
