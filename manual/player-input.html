Player input

Read a player’s action in two lines:

using CodeSmile.LunyScript;

public sealed partial class Shooter : Script
{
    [Variable] public Number Shots { get; private set; }

    protected override void Build()
    {
        var fire = Input.ForPlayer(0).Button("Fire");

        On.FrameUpdate(If(fire.IsPressed).Then(Shots.Add(Time.Delta)));
    }
}

"Fire" is the action name as your Input System action asset spells it. The first local player is index 0.

Declaring an action

Input.ForPlayer(n) returns the surface for one local player. Its four calls declare an action and give you back a handle to read:

Call What it declares Reads as
.Button(name) A button action. IsPressed as a condition, Value as a number.
.Number(name) An axis or analogue action. Value as a number, 0 at rest.
.Vector2(name) A two-axis action. Value as a Vec3 whose Z is 0.
.Vector3(name) A three-axis action. Value as a Vec3. 
var fire   = Input.ForPlayer(0).Button("Fire");
var throttle = Input.ForPlayer(0).Number("Throttle");
var move   = Input.ForPlayer(0).Vector2("Move");
var aim    = Input.ForPlayer(0).Vector3("Aim");

On.FrameUpdate(
    If(fire.IsPressed).Then(Firing.Set(true)),
    Speed.Set(throttle.Value),
    Direction.Set(move.Value),
    AimPoint.Set(aim.Value));

Vector2 and Vector3 are the Input System’s control type names, which is why they carry those spellings rather than the product’s own Vec2 and Vec3.

The player is an index, from 0 upwards, that pairs a device set to a local player. A negative index is refused while Build() runs. Declaring the same player, name and kind twice is one declaration; declaring one name as two kinds is refused while Build() runs. The Input System’s Axis and Analog control types both map onto Number.

Watching an action

A watch runs blocks at one of the Input System’s three phases, so a press is handled once rather than on every frame it is held:

When.Input(fire).Started(Charging.Set(true));
When.Input(fire).Performed(Shots.Increment());
When.Input(fire).Canceled(Charging.Set(false));

Canceled runs on the frame the control returned to rest without having performed. It carries one L, matching the Input System’s own spelling.

Rebinding

An interactive rebind captures the next control the player uses and assigns it to the action. It takes more than one frame, so its outcome is observed through an operation handle:

Operation Rebinding;

protected override void Build()
{
    Rebinding = Operation.Define(nameof(Rebinding));
    var fire  = Input.ForPlayer(0).Button("Fire");

    On.Message("StartRebind", fire.Rebind().As(Rebinding));

    When.Operation(Rebinding).Succeeded(Prompt.Set("Bound."));
    When.Operation(Rebinding).Failed(Prompt.Set("Nothing was bound."));
}

The cursor

Cursor lock and visibility are machine-wide writes, so four local players share one cursor.

Input.Cursor.Lock();       // CursorLockMode.Locked
Input.Cursor.Unlock();     // CursorLockMode.None
Input.Cursor.Show();
Input.Cursor.Hide();

If(Input.Cursor.IsLocked).Then(Crosshair.Set(true));
If(Input.Cursor.IsVisible).Then(Pointer.Set(true));

Lock and visibility are separate settings, so a locked cursor can still be visible. The last write wins. Before any write, the cursor is unlocked and visible.

What an open input gate changes

An input gate makes every action read return its resting value, so IsPressed reads false and Value reads 0 or Vec3.Zero, and it makes every action occurrence read false. It leaves interactive rebind capture running and leaves the cursor as it is, so a rebinding screen can hold the gate open while it captures.

Gate.Open("Menu", GateCategory.Input);
// fire.IsPressed now reads false however hard the player holds the button.
Gate.Close("Menu");
